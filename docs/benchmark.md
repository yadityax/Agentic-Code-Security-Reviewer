# Benchmark methodology

Results live in [results.md](results.md) (generated). This file explains what was measured and how far to trust it.

## Corpus

28 small, self-contained Python projects generated by `benchmarks/build_corpus.py` (`make corpus`). Each has
functional tests that pass on the vulnerable code. 20 contain vulnerabilities (26 ground-truth entries
after revisions, listed with file, CWE and line); 8 are **safe look-alikes** (parameterised SQL, allow-listed
commands, escaped output, a fake token in a test file) that exist to measure false alarms.

Classes: SQL injection (×3), XSS (×2, one also template injection), command injection (×2), path traversal
(×2), SSRF (×2), hardcoded secrets, weak crypto, weak randomness, insecure deserialization (×2), broken
access control (IDOR, missing auth), vulnerable dependencies, container misconfiguration.

13 cases include a hidden **exploit test** that fails on the vulnerable code and passes only once the
vulnerability is genuinely fixed. The system under test never sees it. It is the independent oracle for
remediation.

### Splits

* **dev** (16 cases): used while building. Prompts, custom Semgrep rules and guards were written by reading failures here.
* **heldout** (12 cases): written in a different style (different frameworks and API shapes: FastAPI, `str.format`, `urllib`, `Markup`, `send_file`, `yaml.Loader`), and **not run until the dev work was frozen**. The headline numbers come from here.

## Systems

| | |
|---|---|
| **A** LLM-only | project files in one prompt, no scanners, no tools |
| **B** Scanner-only | Semgrep, CodeQL, Gitleaks, Trivy, Syft, correlated; every finding reported |
| **C** Agentic | B plus analyst triage (drops findings judged false positive) |
| **C+** Agentic + discovery | C plus the LLM logic-flaw pass |

## Scoring

* A prediction matches a ground-truth entry if the file is equal, the CWE is in the same **family** (`backend/services/cwe.py`; e.g. CWE-73 counts for path traversal), and the line is within 6 (any line for manifests and Dockerfiles).
* **One-to-one**: a prediction explains at most one vulnerability, and extra predictions of the same issue are false positives. This penalises duplicate reporting.
* Findings below **medium** severity are not counted for any system.
* Dependency findings are collapsed to one prediction per vulnerable package.
* **Safe apps wrongly flagged** = share of the 8 safe cases where a system reported anything.
* Token/cost/latency are per review. The benchmark shares one rate limiter (7,000 tokens/minute) across concurrent cases, so latency in concurrent runs includes queueing; the held-out run is sequential for that reason.

## Ground-truth revisions (disclosed)

The dev split was corrected once after the first run, because the first run showed the *corpus* was wrong, not only the systems:

1. `xss_flask`: the line is also a **server-side template injection** (`render_template_string` on concatenated input). Tools reporting it were right. A second ground-truth entry (CWE-1336) was added.
2. `pickle_deser`, `ssrf_requests`: returned attacker-controlled data as HTML, an **unintended XSS**. Responses were changed to JSON. The same design flaw was fixed in the held-out `h_ssrf_urllib` case *before* any held-out run, since it was visible without running anything.
3. Scoring bugs found by unit tests: package-level dependency predictions carried a per-CVE CWE; a Dockerfile weakness labelled `CWE-1104` by an LLM was counted as a miss; CWE family canonicalisation.
4. The `docker_misconfig` and `vuln_deps` cases list one entry per weakness / vulnerable package.

No held-out ground truth was edited after seeing held-out results.

## Threats to validity

* **Synthetic, tiny, single-language.** Real repositories are larger, messier and have more false-positive surface. Precision on real code will be lower.
* **Author bias.** One person wrote the vulnerabilities, the fixes for the custom rules and the prompts. The held-out split reduces, not removes, this.
* **Small n.** 12 held-out cases with about 12 ground-truth vulnerabilities: a single case moves recall by 8 points. Compare systems, not decimals.
* **LLM nondeterminism.** Repeated held-out runs use independent caches to show the spread.
* **Tuned rules.** The custom Semgrep rules (hardcoded credentials, SQL from a function parameter, unsafe YAML loader) were added after the dev results; they help B and C equally.
* **Groq-hosted open model.** A frontier model would likely change A and C+ more than B.
